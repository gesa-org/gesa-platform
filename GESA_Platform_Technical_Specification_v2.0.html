VentVestGESA Platform — Technical Specification

1. Overview

GESA (Global Emotional Support Alliance) is a nonprofit platform connecting people in need of emotional support with a global network of verified volunteer therapists, at no cost to the client. The platform consists of a public marketing/intake site, a set of client-facing tools (accounts, chat, session booking, donations), a full therapist self-service dashboard (new since v1.7), and an internal CRM/admin dashboard for staff to manage therapists, submissions, scheduling, payments, and site content.

Stack at a glance: Next.js 14 (App Router, TypeScript) on Vercel, Supabase (Postgres, Auth, Storage, Realtime) as the backend, Resend for transactional email, Mollie and PayPal for payments, and an Anthropic-powered AI matching engine with a rule-based fallback.

Repository conventions: all work is tracked as sequential numbered "Phases" in EXECUTION_PLAN.md, each ending with a review gate before the next begins. As of this document, 208 phases have shipped. No migration files are kept in the repository — every schema change is applied directly to the live Supabase project, with its rationale recorded only in the corresponding phase entry; EXECUTION_PLAN.md is therefore the authoritative schema changelog, not a supabase/migrations/ folder. The codebase favors editing existing files over deleting them — deprecated components/fields are commented as unused rather than removed.

This version (v2.0) supersedes v1.7 in full. Two other markdown specification drafts exist in the repository root (GESA_TECHNICAL_SPECIFICATION.md and GESA_Platform_Technical_Specification_v2.md) — both predate Phase 200 and should be treated as superseded by this document.

2.4 Row-Level Security Pattern & Known Gaps

The core pattern from v1.7 is unchanged (public insert / no public read / admin+reviewer read / admin-only status writes / narrower therapist-read policies). Several things have been added or discovered since and should be part of QA's security pass:

  • New DB triggers: protect_therapist_sensitive_fields() (Phase 186, extended Phase 208) prevents a therapist from self-editing their own lifecycle fields (is_verified, is_active, profile_status, etc.) and — as of Phase 208 — the 4 new calendar-embed columns, restricted to admin/super_admin only, not even reviewer. protect_profile_role_column() (closing a real vulnerability, see below) prevents a signed-in user from setting their own role. protect_last_super_admin() guarantees a role change or delete can never leave zero super_admin accounts.
  • Two real vulnerabilities were found and fixed pre-Phase-187 — worth a regression test each: (1) handle_new_user() used to auto-grant the therapist role to any public signup whose email matched an existing therapist's public contact email; every public signup now always receives role: 'client'. (2) The profiles_self_update RLS policy had no WITH CHECK restricting which columns a user could change on their own row — a client could previously have set role = 'admin' on themselves via a direct request. Both are closed; QA should attempt both again as regression checks.
  • Open item — admin vs. super_admin check gap: several policies/routes still check the literal auth_role() = 'admin' instead of IN ('admin','super_admin'), which silently excludes a valid Super Admin account from some actions (confirmed still open in ImageUploadField.tsx's storage policy and app/api/admin/inquiries/delete/route.ts). QA should specifically test every admin-only action while signed in as a super_admin account, not only as admin — this class of bug only reproduces for that role.
  • Open item — RLS fully disabled on 3 tables in Production: gesa_therapist_photo_map, gesa_group_registrations, gesa_zoom_enrollments. Flagged, not yet remediated.
  • Open item — a parallel legacy gesa_-prefixed schema exists (gesa_site_content, gesa_faqs, gesa_testimonials, gesa_therapists, etc.) sitting alongside the tables the live app actually reads. Not cleaned up. A database audit that doesn't know to ignore these will produce false findings — worth a note to any external security reviewer.
  • support_requests deliberately has zero RLS policies — by design, not oversight — it is only ever read/written through server-side API routes using the service-role client, since it collects more sensitive free-text data (a "feelings" field) than any other submission table.

10. Functional Requirements

All FR-1 through FR-32 from v1.7 remain valid and unchanged unless noted below. New requirements derived from the codebase as of Phase 208:

  • FR-33 — The system shall accept one-time and recurring donations via Mollie, recording status, amount, currency, and payment references in a donations table.
  • FR-34 — The system shall support a paid "Professional Services" booking path (Community page) via PayPal, tagged distinctly from free "Charity" bookings via diary_scheduling_events.service_type.
  • FR-35 — The system shall provide a Media Library allowing admins to upload, tag (alt text/caption/credit), and reuse images across editable page sections, and shall block deletion of an image still in use.
  • FR-36 — The system shall allow admins to manage a list of Trusted Partners (name, logo, link, active flag, order) rendered in the site Footer, falling back to static labels when none are configured.
  • FR-37 — The system shall support grouping FAQ entries by category, rendering a flat list when only one category exists.
  • FR-38 — The system shall render a branded 404 page and dedicated segment/root error boundaries instead of a default framework error screen.
  • FR-39 — The system shall track and display an aggregate, privacy-safe (hashed, non-PII) count of profile views per therapist, visible to the public and mirrored exactly in the admin CRM.
  • FR-40 — The system shall let a therapist view a read-only embed of their own external calendar inside their GESA dashboard when an admin has configured and enabled a provider-approved embed URL for their account, with a secure fallback when embedding is not possible (see §12.3).
  • FR-41 — The system shall provide a full therapist self-service dashboard (Dashboard, My Bookings, My Diary, Notifications, Profile/Settings), gated to the therapist role and scoped so a therapist can only ever see their own data.
  • FR-42 — The system shall support invitation-only onboarding for Administrator and Super Admin accounts, with a time-limited, single-use, hashed token and Resend/Revoke actions.
  • FR-43 — The system shall guarantee at the database level that at least one Super Admin account always exists.

12.3 My Diary — Therapist Diary Calendar Embed NEW — Phase 208

Purpose: let a therapist view their own external, already-booked diary/calendar inside GESA without leaving the site — a private, read-only view of already-scheduled sessions. This is a distinct concept from the pre-existing public diary_link (which clients use to book a new session) — the 4 new columns backing this feature (calendar_embed_url/provider/enabled/updated_at) are never exposed publicly and are trigger-protected so only an admin/super_admin can ever set them (see §2.4/§2.5).

Admin configuration

In each therapist's CRM edit page (TherapistEditForm.tsx), a "My Diary — calendar embed" section lets an admin set the embed URL, pick a provider label (Google Calendar / Outlook / Calendly [marked "embed not supported"] / Other), toggle Enabled independently of the URL, see when it was last updated, and preview the live embed before enabling it for the therapist.

Allowed providers & security model

Only HTTPS URLs on an explicit host allowlist are ever rendered: calendar.google.com, calendar.app.google, outlook.office.com, outlook.office365.com, outlook.live.com — providers with a genuine, documented "publish/embed my calendar as a read-only view" feature. Calendly is deliberately excluded — it has no equivalent "view my own booked events" embed, only a public booking widget (already served by diary_link). Validation runs twice, independently: once when an admin saves, and again immediately before the therapist-facing page ever renders an iframe.

The iframe itself uses a descriptive title ("Therapist diary calendar"), a conservative sandbox attribute (scripts + same-origin + popups only — no top-navigation, modals, or downloads), referrerPolicy="no-referrer", a loading spinner until the frame loads, and an always-visible "Open Diary Securely" fallback button (opens the same URL in a new tab) — not gated behind an error state, since a provider silently blocking embedding via X-Frame-Options/CSP does not reliably produce a JavaScript-detectable error in most browsers.

States a therapist can see on My Diary

  • Not configured — "Your diary calendar has not yet been connected. Please contact the GESA administrator for assistance."
  • Configured but not embeddable (e.g. a stale/invalid saved link) — a safe fallback message plus an "Open Diary Securely" button; the system never attempts to force-render or work around a provider's restriction.
  • Working — the live embed, with an Expand toggle and the same secure "Open" button always available alongside it.

A therapist can never reach another therapist's embed — the page takes no id from the URL or request at all; it is resolved entirely from the signed-in session.

12.4 Notifications & the Header Bell

The shared header Notification Bell (unchanged in its core fetch/polling behavior — see §6) gained, additively, "View in Calendar" (→ My Bookings) and "Open my diary" (→ My Diary) links inside a therapist's own session-notification detail view. The same two links appear on the new full-page Notifications section.

12.5 Booking Synchronization — explicitly not automated

session_bookings remains the sole source of truth for real GESA appointments. The diary embed is view-only: it creates no booking records of any kind, and there is currently no integration that pushes a GESA booking into a therapist's external calendar, or vice versa. Any future such integration is out of scope for this document and should not be assumed by QA.

12.6 Open items

  • Availability (therapist_weekly_hours) is still admin-managed only — the new dashboard does not yet let a therapist edit their own recurring hours.
  • The Profile/Settings section is deliberately read-only for professional details (bio, credentials, photo) — a therapist who needs those changed still contacts the GESA team.
