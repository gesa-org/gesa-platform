1. Overview

GESA (Global Emotional Support Alliance) is a nonprofit platform connecting people in need of emotional support with a global network of volunteer therapists, at no cost to the client for most pathways. The platform consists of a public marketing/intake site, a donation/payments track (Mollie for donations, PayPal for paid Professional Services bookings), a set of client-facing tools (accounts, real-time chat, two distinct booking mechanisms), a full therapist self-service dashboard (five sections, described in §12), an invitation-only onboarding system for therapist and admin accounts, and an internal CRM/admin dashboard with 16 sections including a visual page-content/design-token editor ("UI Builder").

Stack at a glance: Next.js 14.2.3 (App Router, TypeScript) on Vercel, Supabase (Postgres, Auth, Storage, Realtime) as the backend, Resend for transactional email, Mollie for donations, PayPal Orders v2 for paid bookings, and an optional Anthropic-powered AI matching engine with a deterministic rule-based fallback.

Repository conventions (unchanged since v1.0): all work is tracked as sequential numbered "Phases" in EXECUTION_PLAN.md, each ending with a review gate before the next begins. The codebase favors editing existing files over deleting them — deprecated components/fields are commented as unused rather than removed. There is no committed migration history after the initial schema file; every schema change since roughly Phase 126 was applied directly to the Production Supabase project via a database tool, not via a versioned migration file (see §15).

What has materially changed since v1.0 (headline items — full detail in the sections below)

  • Therapists now have a self-service login and a full five-section dashboard at /therapist (v1.0 said no such thing existed at all).
  • Therapists can now view their own external diary/calendar embedded inside GESA ("My Diary," Phase 208) without leaving the site, alongside a real Notifications page and account settings — not just a read-only bookings list.
  • Therapist and admin accounts can only be created via a single-use invitation (Phase 187) — public signup produces client accounts only.
  • A real donations payment flow (Mollie) and a paid "Professional Services" booking flow (PayPal) now exist.
  • The "Find Your Therapist" experience was rebuilt three times and now lives behind a modal launched from /find-your-therapist.
  • A visual design-token and page-content editor ("UI Builder") was added, and the older Content Manager's ~18 tabs were reorganized into four labeled groups (Phase 205) for usability.
  • A therapist profile-view counter now shows publicly on every professional's directory card (Phases 206–207), privacy-safe and session-deduplicated.
  • Two real, disclosed security vulnerabilities (role self-escalation) were found and fixed in Production, and a third, narrower one (self-service diary-embed configuration) was pre-empted at the database level before it could exist (Phase 208).
  • A site-wide hydration failure that made the entire site non-interactive for any visitor with "reduce motion" enabled was found and fixed.
  • A mobile-responsiveness audit and fix pass is underway (Phase 199) but far from complete (§14).
  • A branded 404 page and dedicated error boundaries now exist site-wide (Phase 204).

The four-client model (browser, server, admin/service-role, session-refresh middleware) is unchanged in shape. middleware.ts performs no role gating — it only refreshes the session cookie; all authorization is enforced per-route/per-layout server guards plus Postgres RLS.

2.4 Row-Level Security Pattern

The original five-point pattern (public insert / no public read / admin+reviewer read / admin-only update / narrower therapist-read) is still the general shape, with real, disclosed exceptions:

  1. support_requests has zero RLS policies at all, by design (Phase 142) — it contains an open-text "how are you feeling" field. Service-role-only end to end.
  2. booking_intake_forms has RLS enabled with no public INSERT/UPDATE policy (Phase 128) — writes go through /api/booking-intake using the service-role client.
  3. Fixed vulnerability — role self-escalation via signup metadata (Phase 178). handle_new_user() used to trust raw_user_meta_data->>'role'; anyone calling the Auth REST API directly could pass role: "admin" and be granted admin on signup. Fixed — now always client.
  4. Fixed vulnerability — role self-escalation via profiles self-update RLS (Phase 187). The self-update policy had no WITH CHECK, so a signed-in client could directly update profiles set role='admin'. Fixed via a new trigger, protect_profile_role_column().
  5. Therapist contact-info confidentiality (Phase 126). contact_email/contact_phone revoked from anon at the column level; the new therapists_public view excludes both. get_therapist_contact() (SECURITY DEFINER) is the only read path. A real, live leak (/api/match returning contact_phone to every visitor) was found and fixed here too. Known, still-open gap: a signed-in authenticated therapist account can still select * the base table and read another therapist's contact info — not fixed as of Phase 199 or 208.
  6. therapists gained column-level write protection via protect_therapist_sensitive_fields() (Phase 178, extended 186 for profile_status/volunteer_application_id, and extended again in Phase 208 — see below).
  7. gesa_admin_audit_log RLS tightened (Phase 186) — admin-only INSERT, admin/reviewer SELECT, no UPDATE/DELETE (immutable by design).
  8. protect_last_super_admin() (Phase 187) prevents a role change or deactivation from leaving zero super_admin rows.
  9. Several trigger-only SECURITY DEFINER functions had EXECUTE revoked from anon/authenticated after being found auto-exposed as callable RPC endpoints (Phases 178, 179, 187).
New in Phase 208 — therapist diary-embed configuration is pre-emptively locked down. protect_therapist_sensitive_fields() was extended so that, unless the caller's auth_role() is admin or super_admin (not even reviewer, which is otherwise allowed for several of the fields above), any attempted write to calendar_embed_url, calendar_embed_provider, calendar_embed_enabled, or calendar_embed_updated_at is silently reverted to the prior value — on both INSERT and UPDATE. This means a therapist can never set or enable their own diary embed, and can never target another therapist's row, even via a crafted direct Supabase client request. Because this rule was built at the same time as the feature itself, there was never a window in which self-service escalation on this specific surface was possible — unlike items 3, 4, and 5 above, which were real, live vulnerabilities discovered after the fact.

4. Email System

lib/email/resend.ts's sendEmailSafely() remains the single choke point for every outbound email: a missing RESEND_API_KEY makes it a no-op ({ skipped: true }), any send error is caught and logged rather than thrown, and the underlying database write always happens first and is never rolled back by an email failure.

Architecture change (Phase 177): eight routes used to each hardcode their own || "hello@gesa.org" fallback. This is now centralized in getContactInbox(), the single source of truth for the admin-notification recipient — it validates the environment variable's format and, if missing/invalid, falls back to gesa.org26@gmail.com (hello@gesa.org is fully retired). isValidEmailFormat() also rejects header-injection attempts. lib/contact.ts exposes a separate public-display address, kept apart from the server-only contact inbox.

  • FR-79 — The system shall let an administrator manage a Trusted Partners list (logo, link, sort order, active flag) shown in the public footer, falling back to the original static labels when the list is empty.
  • FR-80 — FAQ entries shall support an optional category, and the public FAQ page shall group entries by category only when more than one distinct category exists.

  • FR-83 — The public profile-view counter shall be denormalized onto the therapist's row and kept atomically in sync with its underlying event table, such that the two can never drift; the same counter value shall be shown both publicly and in the CRM's analytics view.

  • FR-86 — The therapist dashboard shall present Dashboard, My Bookings, My Diary, Notifications, and Profile/Settings as distinct, independently guarded sections; a therapist without a linked professional profile shall see a clear message rather than a broken or empty dashboard on any of the five.
  • FR-87 — The diary calendar embed shall never create, duplicate, or modify any GESA booking record; session_bookings shall remain the sole source of truth for confirmed appointments regardless of what the embedded external calendar shows.

12. Therapist Workflow MAJOR UPDATE — PHASE 208

This section has changed more than any other since the original v1.0 specification. v1.0 stated, in its own words, that "Therapists do not have a self-service portal" and have "no login flow distinct from the generic client sign-in." That was corrected as of Phase 199 (a read-only, single-page dashboard existed since Phase 127). As of Phase 208, the dashboard has been rebuilt entirely into a five-section experience, and this section should be read in full even by anyone who already tested the therapist dashboard before this phase.

12.1 Account creation — invitation-only

Account creation is invitation-only (Phase 187, current model). An admin sends a single-use, expiring, cryptographically hashed invitation (individually, in bulk, or automatically when approving a volunteer application). The invited person accepts it at /accept-invitation, sets a password, accepts Terms and Privacy, and is signed in and redirected straight to /therapist. Public self-registration can never produce a therapist or admin account. Two earlier, less secure mechanisms (manual admin linking, then a brief email-matching auto-link that was found to be a real security hole and removed) preceded this one — see the version history in §2.4 for the underlying RLS/trigger detail.

12.2 The five-section dashboard

Reached at /therapist, gated end-to-end by requireTherapist() (app/therapist/layout.tsx), with a new sidebar (components/therapist/TherapistNav.tsx, mirroring the admin sidebar's own pattern) presenting exactly these five sections, in this order:

12.3 My Diary — the Therapist Diary Calendar Embed feature

Lets a therapist view their own external diary/calendar directly inside GESA, without opening another tab, for the specific purpose of reviewing their own scheduled sessions. This is conceptually and technically separate from the existing public diary_link field (§3.3, §5.4), which is what a client uses to book a new session — the two were never meant to solve the same problem and this feature does not touch or replace that one.

Three page states on /therapist/diary

StateConditionWhat the therapist sees
Not configuredcalendar_embed_url is null, or calendar_embed_enabled is false"Your diary calendar has not yet been connected. Please contact the GESA administrator for assistance."
Configured but invalidA URL is saved and enabled, but no longer passes the embed allowlist (e.g. a stale or unsupported link)A safe fallback message plus an "Open Diary Securely" button. The system never attempts to force-render a URL that fails validation.
Configured and validURL set, enabled, and passes the allowlistThe live embedded calendar (DiaryEmbed component) — see below.

The embed itself

  • Allowlisted providers (lib/diary/embedAllowlist.ts): calendar.google.com, calendar.app.google, outlook.office.com, outlook.office365.com, outlook.live.com — HTTPS-only. Calendly is deliberately excluded — it has no "view my own booked events" embed, only a public "book a new time" widget (already the role of diary_link). The admin's provider dropdown labels Calendly "embed not supported" so this reads as an intentional limitation, not a bug.
  • Security: descriptive iframe title ("Therapist diary calendar"), responsive height (520px mobile-friendly up to 620px desktop, with an Expand toggle to 85% viewport height), sandbox="allow-scripts allow-same-origin allow-popups allow-popups-to-escape-sandbox" (no top-navigation, no modals, no downloads), referrerPolicy="no-referrer", a loading spinner shown until the iframe's onLoad fires.
  • Always-visible fallback: an "Open Diary Securely" button (opens the same URL in a new tab, noopener,noreferrer) is shown at all times alongside the embed, not only when something fails — because a provider silently blocking iframing via X-Frame-Options/CSP does not reliably raise a JS-detectable error in most browsers, there is no fully reliable way to know from the client side whether an embed has actually been blocked. This design choice means a therapist is never stuck looking at a broken frame with no way forward.

Access control

Only an Administrator or Super Admin can set, update, enable, disable, or clear a therapist's calendar_embed_url/calendar_embed_provider/calendar_embed_enabled — enforced by the extended protect_therapist_sensitive_fields trigger (§2.4), not merely hidden in the UI. A therapist's diary page takes no id from the URL or request at all — it always resolves to the signed-in session's own linked therapist record, so there is no parameter a therapist could tamper with to reach another therapist's diary. No GESA client details, mental-health information, or private assessment answers are ever shown in the diary page's own wrapper/interface — the embed shows only the therapist's own external calendar content.

Booking synchronization — explicitly one-way and read-only

The embed does not create, push, or synchronize anything into a therapist's external calendar, and nothing about a GESA booking is automatically sent to it. session_bookings remains the sole source of truth for confirmed GESA appointments; the diary page itself carries a standing footnote: "This is a read-only view of your external calendar. It does not create or change GESA bookings." If a real, two-way integration is ever built in the future, the existing booking id would need to become the synchronization key to prevent duplicate external events — no such integration exists today, and this document does not claim one does.

12.4 What a therapist still cannot do — unchanged by Phase 208

Editing their own bio/credentials/photo/specialties, confirming/cancelling/rescheduling a booking, or managing their own availability, pricing, or offered pathways/session types all remain exclusively admin functions through the CRM. There is still no in-app queue for a therapist to accept or decline a request — coordination with clients still happens by email, WhatsApp, or Zoom outside the platform. Availability remains an entirely admin-managed record (therapist_weekly_hours), with no therapist-facing editor.

12.5 Known, still-open gap

The site-wide notification bell's therapist-facing branch still only surfaces the legacy match_requests table and has never been extended to real session bookings or scheduling-link events (flagged since Phase 127, still open). Phase 208 does not fix the bell's own data source — it adds "View in Calendar" and "Open my diary" links to the bell's existing notification detail modal (and to the new full-page Notifications list) so that whatever the bell does surface has a fast path into the real dashboard, without changing what the bell decides to show in the first place.
